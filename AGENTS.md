# AGENTS.md

This file provides guidance to AI agents when working with code in this repository.

## Project purpose

A sample Android app (`uno.lux.sample`, displayed as "Sample") built as a resume/portfolio piece to demonstrate modern Android architecture. Code quality, idiomatic Compose, and architectural clarity are the point of the project, not just working features — prefer the current, recommended Android way of doing things over expedient shortcuts.

## Testing philosophy — tests first

Tests are the **primary consumer** of this codebase; real users come second. Production code exists first to satisfy a test — we write the code that makes tests pass, and only then does it also happen to serve users. In practice:

- **Write the test first.** Express the desired behaviour as a failing test, then write the code that makes it pass. A change isn't done until tests cover it and they're green; new logic lands with its test in the same change.
- **Design for the test.** Keep logic in plain-JVM, dependency-injected units so a test can drive it directly. The `data` layer and ViewModels take their collaborators as constructor parameters and avoid Android dependencies; pure functions take their inputs (e.g. `now`) as parameters instead of reading ambient state. This is *why* the architecture is shaped the way it is — testability drives the design, not the other way round.
- **Same rule for UI.** Stateless composables take data + callbacks so they can be exercised in isolation; ViewModels expose state as a `StateFlow` a test asserts against.

Run the unit suite with `.\gradlew.bat testDebugUnitTest` (single class: `--tests "uno.lux.sample.app.util.RelativeTimeTest"`).

Shared test infrastructure lives in `app/src/test/java/uno/lux/sample/testing/`: `MainDispatcherRule` (swaps `Dispatchers.Main` for a test dispatcher), `ViewModelTest` (the base class ViewModel tests extend), `BackStacks` (`backStackOf`/`screens`, for driving the `Navigator`) and `TestUtils`. Fakes are hand-written and live beside the thing they stand in for (`post/data/FakePostDataSource.kt`, `post/data/network/FakePostApi.kt`) — there is no mocking framework.

## Toolchain / build setup

- **Kotlin 2.4.10**, **AGP 9.3.1**, **Gradle 9.6.1**, Compose BOM **2026.06.01**.
- `compileSdk` is **37**, expressed with the newer AGP DSL `release(37)`; `minSdk = 26`, `targetSdk = 36`. `core-ktx` 1.19, `lifecycle` 2.11 and `androidx.hilt` 1.4 all *require* compiling against 37, which is why it moved ahead of `targetSdk` — raising `compileSdk` only widens the APIs available at compile time, while `targetSdk` is what opts the app into new runtime behaviour, so the two are bumped separately. Lint's `OldTargetApi` warning is the expected cost of that gap.
- Source/target compatibility is **Java 11**, but the Gradle daemon runs on **JDK 21** (`gradle/gradle-daemon-jvm.properties`, auto-provisioned via foojay).
- AGP 9's **built-in Kotlin** is in use — there is no standalone `org.jetbrains.kotlin.android` plugin. Annotation processing runs through **KSP** (kapt is incompatible with built-in Kotlin); Hilt's codegen rides on it.
- AGP 9.3.1 still *bundles* Kotlin 2.2.10; the root `build.gradle.kts` puts a newer `kotlin-gradle-plugin` on the **buildscript classpath** (the documented override) to lift the compiler to **2.4.10**. The Compose compiler and kotlinx-serialization plugins are version-locked to that Kotlin (`version.ref = "kotlin"`) and must move with it, as must **Mappie** (`<kotlin>-<mappie>`, used for DTO → domain mapping in `post/data/network/PostMappers.kt`) — a Kotlin bump is blocked until Mappie publishes a matching build. **KSP is no longer locked to Kotlin**: KSP2 versions independently (`2.3.10`, not `<kotlin>-<ksp>`) and spans a range of compiler versions, so it moves on its own schedule.
- Dependencies are managed through the **version catalog** at `gradle/libs.versions.toml`. Add or bump dependencies there and reference them via the generated `libs.*` accessors in `app/build.gradle.kts` — do not hardcode versions in the build script.

## Backend

The app talks to a **Rails** backend at `https://mosaic.tree-among-shrubs.com/api/` (`BASE_URL` in `app/di/NetworkModule.kt`); its source is the `mosaic-server` repo, checked out under WSL at `\\wsl.localhost\ubuntu\home\benji\projects\mosaic-server`. There is **no sign-in**: the signed-in user is seeded from `app/fixtures/SampleData.kt` and sent as an `X-User-Id` header on every request, which is what the server scopes viewer state (`isLiked`, `isBookmarked`) by and what it enforces ownership with — deleting someone else's post and reading someone else's bookmarks both 403 on the server, not merely in the client. Client-side limits (`CreatePostMaxImages`, `CreatePostMaxVideoBytes`, the composer's field lengths) mirror server validations; changing one means changing both.

**Reporting a post is a request the server checks and then forgets.** `POST /api/posts/:id/report` validates that the post exists and that the reason is one of `PostsService::REPORT_REASONS`, then logs and discards the report and answers an empty 204 — there is no moderation queue to store it in. That list mirrors the client's `ReportReason` enum and `REPORT_DETAILS_MAX_LENGTH` mirrors the details cap on the dialog's text field, which matters more here than elsewhere: the report goes out fire-and-forget and the "thank you" is optimistic, so a report the server would refuse must not be typeable in the first place. The reason's *wire* spelling lives with the wire types, in `post/data/network/ReportPostRequestDto.kt`, so the domain enum stays free of it; blank details are left off the body entirely rather than sent as an empty string.

## Package structure — where a new file goes

The top level is **slices, not layers**; layers are the shape *inside* a slice. There is no `data/` or `ui/` root package, and deliberately no `activities/`, `fragments/`, `viewmodels/`, `adapters/` or `dialogs/`: **a file's home is decided by what it is *about*, never by what it extends.** Supertype is what the IDE indexes for you; it never needs a folder.

**The top level is the product itself.** `app/` is the machine — scaffolding and plumbing, holding no feature. `common/` is what the concerns share, and it sits at the top level rather than under `app/` because *being shared is not the same as being infrastructure*: a noun-free dialog is not part of the machine.

```
post/ user/ comment/ album/ video/   aggregates: the entity, its wire types, its store, its UI
feed/ profile/ composer/ settings/   read models and features — they own no entity

common/         what the concerns share — ui/ noun-free composables, data/ wire types and files
app/            the machine — MainActivity, MosaicApplication, MosaicApp, the shell
app/di/         Hilt modules; app/navigation/  Navigator + the Screen keys + BackStackEntry
app/theme/      the Mosaic palette, type and gradients — no domain noun
app/util/       pure functions with zero project imports (plus small Kotlin/Android extensions)
app/fixtures/   stand-in content for previews and DI seeding
```

Inside a concern the shape is fixed, and `ArchitectureTest` enforces it — there are four layers and no fifth:

```
<concern>/data/            the repository and its DataSource interface
<concern>/data/domain/     the models — pure Kotlin, no platform and no wire
<concern>/data/network/    the service, DTOs, mappers — the only place HTTP appears
<concern>/ui/              composables and ViewModels
```

**Aggregates vs read models** is the distinction that keeps the graph directed. `post`, `user`, `comment`, `album` and `video` own an entity and everything about it. `feed` and `profile` own no entity — they are read models over those stores, holding an ordered list of IDs plus paging state, which is why `ProfileRepository` *composes* `PostRepository` instead of duplicating it. `album` and `video` are aggregates that happen to be leaves: `post` depends on them, they depend on nothing but `app`. The rule, worth preserving:

> Features may depend on aggregates. **Aggregates never depend on features.**

The actual cross-slice graph, which any new import should be checked against:

```
user  album  video  settings  -> (nothing)
post      -> album comment user video      comment  -> post user
feed      -> post settings user video      profile  -> post user video
composer  -> feed post
```

(Every slice may depend on `app`; nothing under `app` may depend on a slice.)

Two feature-to-feature edges are deliberate: `composer -> feed` (publishing prepends the new ID to the feed) and `feed -> settings` (the auto-play preference). **`post <-> comment` is a real cycle** — a comment needs a `PostId` and `PostDetailScreen` renders comments. `Comment` is arguably an entity *inside* the post aggregate rather than a root of its own (it cannot exist without its post and is deleted with it), so folding `comment/` into `post/` is the fix if the cycle ever bites; it stays separate while it earns its own folder.

Two things that look like violations but are not, and should not be reintroduced: a KDoc `[Link]` needs an import, so cross-slice doc references are written fully qualified (`[uno.lux.sample.profile.data.ProfileRepository]`) rather than imported; and a wire type shared by two features belongs to the aggregate it describes, not to whichever feature happened to declare it first — `SideloadedUsers` is a list of `UserDto`, so it lives in `user/data/network/` and both `feed` and `profile` depend *down* onto it. A wire type that belongs to *no* single aggregate goes to `common/data/network/` instead — `LikeToggleDto` is the `{ isLiked, likeCount }` envelope posts *and* comments both answer a heart with, while bookmarking, which only posts do, stays in `post`.

To file a new file, ask in order — no two questions tie:

1. **Does it mention a domain noun?** No → 2. Yes → 3.
2. Pixels → `common/ui` (a colour or a font → `app/theme`). Wires the app together → `app`. Neither → `common/data`/`app/util`.
3. Claimed by exactly one feature → that feature. By several → the noun's aggregate.

Worked examples: `DiscardChangesDialog` knows no noun and is shared by the composer and the profile editor → `common/ui/`. `ReportDialog` knows `ReportReason` → `post/ui/`. `Avatar` renders a `User` → `user/ui/`, not `common/ui/`. `FileLoader` reads content URIs and names nothing → `common/data/files/`. `relativeTime()` imports nothing of ours → `app/util/`. The moment a "helper" imports `Post`, it is post code — file it home.

Inside a slice, `data/` holds the repository and its `DataSource` interface, and `data/network/` holds the service, DTOs, mapper and the `Network…DataSource`. **The interface stays beside its consumer, not beside its implementation** — that is what lets a repository compose a network and a local source without either owning the contract, and it is why `data/network/` is nested inside the slice rather than shared.

**There is one Retrofit service per slice** (`FeedApi`, `PostApi`, `CommentApi`, `UserApi`, `ProfileApi`), all created from the one `Retrofit` instance in `app/di/NetworkModule.kt`. Do not reintroduce a single app-wide API interface: the previous one spanned five slices, so it fit in none of them, and its 338-line fake had to be implemented in full by every test that needed one endpoint.

**These rules are executable, not advisory** — `app/src/test/java/uno/lux/sample/architecture/ArchitectureTest.kt` (Konsist) asserts seven of them against the real source tree and fails the build on a violation. Kotlin has no package-private and `internal` is module-scoped, so nothing else in a single-module project checks this.

**Every rule is derived from the path, never from a list of names.** The concerns are *discovered* — the top-level packages that exist, minus `app` and `common` — and each rule keys off the shape the convention gives them (`<concern>/data`, `/data/domain`, `/data/network`, `/ui`). Nothing declares that `post` is an aggregate or `feed` a read model, so adding a slice requires no edit to the test:

1. **Every concern package follows the convention** — one of the four layers, including files that would otherwise sit loose at a concern's root. This is the rule the rest are built on: they select files by matching those suffixes, so a file in an invented package would be checked by *none* of them.
2. **The wire stays in `data/network`** — Retrofit/OkHttp nowhere else, `app/di` excepted for the one `Retrofit` instance.
3. **The domain layer is pure** — `data/domain` imports no platform, no wire, no screen. The mapper converts DTO → model, never the reverse.
4. **`data` never depends on `ui`.**
5. **`common` knows no concern** — it is what they share, so it may know none of them.
6. **A repository behind no interface stays plain-JVM** — a `*Repository` with no supertype carries no Android import. This is what replaced a hardcoded `settings` exemption, and it states the actual reason: `DataStoreSettingsRepository` and `AppCompatLocaleRepository` may touch the platform *because* they implement an interface their consumers can be handed a double for.
7. **The concern graph holds only the documented cycle** — the import graph is built and searched for cycles, with `post ↔ comment` the single accepted entry.

The failure mode this shape exists to prevent is a rule that silently stops checking. The previous version hardcoded `uno.lux.sample.app.common..`; when `common` moved to the top level the rule kept passing while matching zero files. Rule 1 is the guard — the layout can no longer drift out from under the others without failing. Adding a rule means adding a test; if a violation is *intended*, widen the rule and say why in its message rather than deleting it. Verify a new rule by planting a violation and watching it fail — a green architecture test proves nothing on its own.

## Architecture

Single-activity, 100% Jetpack Compose app — there are no Fragments and no XML view layouts (XML under `res/` is only resources: themes, colors, vector icons, backup rules). The entire UI tree is built in Kotlin.

- **Entry point** — `MainActivity` (`app/src/main/java/uno/lux/sample/app/MainActivity.kt`) is the only Activity and stays a thin shell. In `setContent` it collects the `ThemeMode` preference from `MainViewModel`, resolves the dark/light choice, applies it to `MosaicTheme`, and hosts `MosaicApp()` (`app/MosaicApp.kt`). It extends `AppCompatActivity` for one reason only — AppCompat's delegate is what applies the user's per-app language below Android 13 (see *Localization*) — and uses no AppCompat UI.

- **Navigation — Navigation 3 with a tabbed root shell, driven by ViewModels.** `MosaicApp()` owns a `rememberBackStack` of `@Serializable` `BackStackEntry` keys (`app/navigation/BackStackEntry.kt`), each pairing a `Screen` (`app/navigation/Screen.kt`) with the identity its state is scoped to: `Screen.Shell` is the permanent root, and `Screen.Profile(userId)` (tapping a post's author) or `Screen.Settings` (the gear in any top bar) push over it as full-screen pages — settings stacks over a profile, too. `NavDisplay` renders the top entry with directional push/pop slide transitions, predictive back included; back handling is just `onBack` popping the stack — there are no hand-rolled `BackHandler`s. The entry decorators give every entry its own saveable state and **ViewModel store**, so each pushed page's ViewModel is created on push and cleared on pop (each opened profile gets its own `ProfileViewModel` without manual keying). The back stack survives configuration changes and process death because the keys are serializable.

  **The back stack is a list of positions, not of pages — which is why identity lives on the entry and not on the `Screen`.** Navigation 3 scopes *everything* per entry — the `rememberSaveable` holder, the `ViewModelStore`, the scene — by `NavEntry.contentKey`, and a content key is a function of the back-stack key **alone**: `entryProvider` is handed the key and nothing else, so nothing outside the key can tell two identical entries apart. With a bare `Screen` as the key, `contentKey` defaulted to `key.toString()`, and two pushes of `Screen.PostDetail("p1")` — open a post, walk to its author, open the same post from their profile — collapsed onto one scope: the second page got the first's `PostDetailViewModel` *and* its half-typed comment, because the first saved its `rememberSaveable` state into that slot on the way out and the second restored it. `BackStackEntry(screen, id)` fixes it by making identity a property of the position; `MosaicApp` passes `contentKey = { it.id }`. `Navigator.entryFor` is the only place an `id` is minted, so a new `Screen` cannot forget to take part — the alternative, an `instanceId` on each key, is a per-type obligation the compiler can't enforce, would have to be `@EncodeDefault` (`SavedStateConfiguration.encodeDefaults` is `false`, so a defaulted id is dropped on save and *regenerated* on restore, orphaning the state it keyed), and would break `Screen` equality, which `goToSingleTop` asks about. `rememberBackStack` stands in for `rememberNavBackStack` because both of that one's overloads return a `NavBackStack<NavKey>` serialized through the reflective per-element `NavKeySerializer`; naming `BackStackEntry` keeps the stack typed end to end and moves the polymorphism onto the sealed `Screen` field, where the compiler resolves it.

  **A screen can opt back into sharing, through `Screen.sharedId`.** It is `null` by default — a fresh identity per push — and a screen that overrides it with a constant is one page wherever it is opened, sharing a single ViewModel and one set of `rememberSaveable` state; deriving it from the screen's own arguments (`"post-$postId"`) shares per argument, which is what the app did before entries carried identity — so reach for that form only when a page genuinely *is* one thing per argument, not to restore the old behaviour wholesale. `Screen.Shell` is the only screen that pins one today, being the permanent root. Declare it as `get() = …` and never as an initialized property: a backing field would be pulled into the key's serialized form.
  **Navigation intent flows through the ViewModels**, not host-provided lambdas: *every* screen — the leaf viewers and the composer included — has a ViewModel that injects the `Navigator` (`app/navigation/Navigator.kt`, provided `@ActivityRetainedScoped` in `app/di/NavigationModule.kt` — the pattern from the official Nav3 Hilt recipe) and calls `goTo(screen)` / `goBack()`, so e.g. `EditProfileViewModel` pops the editor itself once a save lands and `AlbumViewerViewModel`/`FullscreenVideoViewModel`/`CreatePostViewModel` route their back/settings affordance the same way. `MosaicApp` therefore wires **no navigation lambdas at all** — it hands `NavDisplay` the shared `backStackEntryProvider` (which is where `contentKey = id` is stated, once, so the instrumented test pins the app's rule rather than a copy of it) with one exhaustive `when` over the sealed `Screen` picking the page: a compile-time check, where the old per-screen `entry<Screen.X>` blocks would only have thrown at runtime on an unregistered key. The `entryProvider { entry<T>() }` DSL is deliberately unused — it dispatches a `KClass`-keyed map between registered key types, pointless with one, and its metadata cache is keyed by the whole key and never pruned, so an identity per push would retain every entry ever pushed along with its `Screen` payload. The composition keeps *owning* the stack — `MosaicApp` attaches the `rememberBackStack` list to the `Navigator` in a `DisposableEffect` — which is what preserves the saveable/process-death guarantee the recipe's self-owned `SnapshotStateList` would lose. Two push variants: `Navigator.goTo` allows pushing a screen equal to the current top (an intentional re-open, e.g. the same profile from a post on it — the 500 ms click debounce every nav control carries covers the accidental double-tap; the re-opened page is a genuinely separate one, with its own ViewModel and state), while `Navigator.goToSingleTop` is a no-op when its screen already sits on top, giving pages that must never stack on themselves (Settings, the profile editor) a real guarantee independent of tap timing — it compares the top entry's *screen*, which is what keeping identity off the key leaves answerable. `Navigator` takes its id source as a constructor parameter (`nextId`, defaulting to a UUID) for the same reason the formatters take `now`; it must not be a counter, since the `@ActivityRetainedScoped` instance restarts on a process death while the restored stack still holds ids minted by the old process. Unit tests drive the real `Navigator` by attaching a stack built with `testing/BackStacks.kt`'s `backStackOf(…)` and asserting on `.screens()`, so an assertion about navigation stays about pages rather than identities.

- **Adaptive navigation inside the shell.** The `Shell` entry hosts `HomeNavShell`: Material 3's `NavigationSuiteScaffold` (via the project's `DividedNavigationSuiteScaffold`) adapts the navigation UI to the window size — bottom nav bar on phones, navigation rail / drawer on larger or unfolded screens — without per-form-factor code. Destinations are data-driven: the `AppDestinations` enum (a `@StringRes` label + icon drawable per entry, plus an optional `screen`: HOME, CREATE, PROFILE) is the single source of truth, and the nav items are generated by iterating `AppDestinations.entries` — add or change a tab by editing the enum. **Tab selection is deliberately plain `rememberSaveable` state, not back-stack entries**: switching tabs is not a navigation event, so system back never walks through tabs. HOME → `HomeScreen` (the feed); the PROFILE **tab** → the signed-in user's own `ProfileScreen` (with no up-affordance — `showBackButton` stays false — since it's a root tab, not a pushed page). **CREATE is deliberately not a tab**: an `AppDestinations` entry carrying a `screen` is an *action*, and selecting it pushes that page over the entire shell through `ShellViewModel` (`goToSingleTop`, so it can't stack on itself) instead of swapping the content area — covering the navigation bar, sliding in like any other page, and never becoming the selection, so the tab underneath stays highlighted. That is the centre "new post" button behaviour of apps like TikTok, and it is why the shell's content `when` has an unreachable `CREATE -> Unit` branch. Each screen owns its own `Scaffold`/`TopAppBar` rather than sharing one, so screens control their own chrome; tab switches cross-fade (fade-through) while page pushes slide.

- **Feature architecture — the HOME feed sets the pattern to follow.** Within a slice, code is layered by responsibility:
  - `<slice>/` and `<slice>/data/` — domain models (`Post`, `User`) and repository interfaces, the seam real implementations slot into. `PostRepository` wraps a `PostDataSource` and holds a `StateFlow<List<Post>>` cache so like/bookmark mutations are instantly reflected across screens without a re-fetch. **Deleting rides the same propagation**: `PostRepository.delete` drops the entity, and because `FeedRepository`/`ProfileRepository` hold only ordered *IDs* that they resolve through that store, the post vanishes from every screen showing it in one emission — the ordered lists are deliberately left untouched rather than kept in step by hand. The affordance lives in the post overflow sheet and is offered only on your own posts; the client gates it on the author ID, and the server enforces it (`DELETE /api/posts/:id`, 403 for a non-author) rather than trusting the client. Deletion cascades to the post's comments/likes/bookmarks, and to an `Album`/`Video` once no post still holds it. `SettingsRepository` has an `InMemorySettingsRepository` (the test double) and the production `DataStoreSettingsRepository`, which persists the theme choice and the video auto-play preference in a Preferences **DataStore**; the store is a constructor dependency, so its unit tests drive a *real* DataStore over a temp file on the JVM. The DataStore itself is provided in `DataModule`; the persisted key `theme_mode` is the contract with the legacy SharedPreferences file it replaced — tests pin it to ensure continuity. An **absent** preference means "never chosen", and what that resolves to is named once, in `DefaultAutoPlayVideos`: `auto_play_videos` reads as **off** when the key is missing, since a feed that starts playing by itself is a thing to opt into rather than out of, and it spends someone's data before they asked. Both the repository and `HomeViewModel`'s `StateFlow` start from that same constant, so a launch never flips playback as the stored choice arrives. Tests on either side deliberately seed the value *opposite* the default, so one that fell through to the default instead of reading the stored choice fails rather than accidentally agreeing. The profile layer adds `Profile` (a user's profile metadata) and `ProfileRepository` — which **composes** a `PostRepository` (a profile's posts are simply the feed posts authored by that user) rather than duplicating mutation logic. `Album` and `Video` are slices of their own (`album/`, `video/`) rather than types inside `post/`: they are attachments a `Post` points at, and keeping them separate makes them leaves that `post`, `feed` and `profile` all depend down onto. Domain models, the interfaces, and every repository implementation carry no Android dependencies, so the whole layer is plain-JVM testable.
  - `feed/ui/` — MVVM with unidirectional data flow. `HomeViewModel` exposes `StateFlow<HomeUiState>` (a sealed interface: `Loading` / `Feed`) and converts intent into repository mutations via `viewModelScope` (`onToggleLike`, `onToggleBookmark`) or `Navigator` pushes (`openPost`, `openProfile`, `openSettings`, the media viewers) — both kinds live on the one `HomeActions` seam the stateless screen depends on. `HomeScreen` is split into a **stateful** binder (collects state, injects the ViewModel) and an **internal stateless** composable (pure inputs + callbacks) so it previews and tests without a ViewModel. `PostCard` and its sub-composables are likewise stateless with hoisted callbacks; the header (avatar / name / handle) is one tappable target that opens the author's profile.
  - `profile/ui/` — the same MVVM split, parameterized by user. `ProfileViewModel` is bound to a `userId` through Hilt assisted injection (a ViewModel can't take runtime args directly), is also given the `@CurrentUserId` signed-in user, and exposes `StateFlow<ProfileUiState>` (`Loading` / `Loaded(profile, isCurrentUser)` / `NotFound`) — `isCurrentUser` is the viewed `userId` matching the signed-in one. `ProfileScreen` is a stateful binder + internal stateless composable: a full-bleed gradient cover with an overlapping surface-ringed avatar, an identity block (age/gender/location chips, bio, follower/following stats, *Edit profile* — shown only on your own profile — + settings), then a **sticky** Material tab row inside the single `LazyColumn`, generated by iterating the `ProfileTab` enum: Posts, Likes and Saved, all reusing `PostCard`. Cover imagery is a deterministic gradient stand-in keyed by id, mirroring `Avatar`.

    **Saved is private and Likes is public — the pair is the point.** A `ProfileTab` carries `ownerOnly`; the row filters on it, so Saved exists only on the signed-in user's own profile while Likes appears on everyone's. That filtering is why the row's selected index is `tabs.indexOf(selected)` and *not* the entry's ordinal. The client gating is a courtesy; the server is the enforcement (`GET /api/users/:id/bookmarks` 403s unless `:id` is the caller, refusing *before* the lookup so an unknown id can't distinguish itself from a real one, while `GET /api/users/:id/likes` serves anyone's to anyone).

    Both lists are fetched **lazily, on first open** (`onSavedTabShown` / `onLikesTabShown`) rather than by `ProfileRepository.refresh`: a tab nobody opened should cost no request, and the private one should never be reached for unasked. `bookmarkIds`/`likeIds` therefore emit `null` until that first load lands — how a tab tells "empty" from "not asked yet" — and a pull-to-refresh re-fetches only what has been opened. The two share one `PostsWithAuthorsPage`, one `PostsWithAuthorsResponse`, and one private `OnDemandPostIds` inside `ProfileRepository`, since only the endpoint differs. **For the signed-in user, each list is derived from its flag rather than echoed from the fetch**: a list defined by `isBookmarked`/`isLiked` *is* the set of `PostRepository.entities` carrying that flag, so `OnDemandPostIds` takes the flag (`Post::isBookmarked` / `Post::isLiked`) and `combine`s it with the entity store. Membership therefore moves in both directions and from anywhere — liking a post in the Posts tab or the feed inserts it into the Likes tab, unliking removes it — with no re-fetch. Deriving only *removal* is the trap to avoid here: it was the first version of this, and it made a post's membership depend on whether it happened to be in a page the server had already sent, so a like from the Posts tab showed up only if the post had previously been liked-then-unliked. Order comes from the server's own keyset, `(createdAt, id)` descending (`Cursor.paginate`), which the client can reproduce because `Post` carries both fields — an inserted post lands where a refetch would put it. Paging is the one limit: `PageState.oldestLoaded` records the floor of the loaded window and a post below it is held back until its page arrives, rather than jumping ahead of posts that outrank it. None of this applies to *another* user's Likes tab, which is echoed exactly as fetched: `isLiked`/`isBookmarked` are viewer-scoped (the server computes them for the caller, not the profile's owner), so on someone else's profile they describe you and say nothing about what belongs on their list — which is why `ProfileRepository` is given `@CurrentUserId`. Unlike a profile's own posts, which are all by the profile's user, a saved or liked post can be by anyone: its author rides along in `included.users` (always sent, unlike the feed's opt-in `include=author`) into `UserRepository`, its card is a ViewModel-built `PostCardData`, and its header opens that author's profile.

    **There is exactly one user projection, and that is load-bearing.** A sideloaded author is serialized identically to a fetched profile — `UserSerializer.serialize` is the only one the backend has. The API used to also serve a `minimal` projection (identity only, profile detail omitted), which on the wire was indistinguishable from a user who had genuinely left those fields empty: `UserRepository.ingest` replaces entries wholesale, so a sideloaded partial user silently blanked the bio, identity chips and follower counts of a profile already loaded in full. It surfaced as an *intermittent* `ProfileHeader` bug, because `ProfileViewModel.load` races `userRepository.refresh` against the saved/likes fetches and only the losing order showed it. The invariant that keeps this fixed is on `User`: a `null` optional field means the user left it empty, never "not loaded yet". Do not reintroduce a partial projection — if a payload ever needs a trimmed user, give it its own type rather than an under-filled `User`. Ordering follows the posts' own recency — the join tables carry no timestamp, and reusing the shared keyset was worth more than save/like-order.

  - **A like is not restricted to other people's posts — an author may like their own.** `PostActions` renders one heart with no owner gating on either surface (the feed/profile `PostCard` and the detail screen), and `PostsService#toggle_like` accepts a self-like like any other. `isOwn` on `PostCardData`/`PostDetailUiState` survives, but it gates *deletion* only.
  - `composer/ui/` — the post composer, pushed over the shell by the CREATE navigation item, using the same stateful-binder + stateless-screen split. `CreatePostViewModel` holds one plain `StateFlow<CreatePostUiState>` (form + in-flight flag + a single `CreatePostError`) rather than a sealed hierarchy, because a composer has nothing to load. There is one error field, not one per source: the screen has a single snackbar, so separate fields would only ever mean "whichever is set" — an invariant kept by convention at every update site instead of by the type. Publishing goes through `FeedRepository.publish`, which calls `PostRepository.create` (storing the entity), ingests the embedded author, and prepends the new ID to the feed so the post is visible without a re-fetch; the ViewModel then `Navigator.replaceTop`s itself with `Screen.PostDetail`, so backing out of the new post returns to the shell rather than to a spent composer. A failed publish keeps the typed text, and leaving with a part-written post raises the shared `DiscardChangesDialog` — the same treatment the profile editor gives unsaved edits. Field limits (`CreatePostTitleMaxLength`, `CreatePostBodyMaxLength`) mirror the backend's `Post` validations so errors surface before the request. **Media is authorable and exclusive — photos or one video, never both.** `CreatePostMedia` (and its data-layer twin `NewPostMedia`) is a closed hierarchy of `None` / `Images` / `Video`, so the illegal combination is *unrepresentable* rather than a rule the form has to remember; the server enforces the same invariant with a `Post` validation and a `media_conflict` 422. The composer therefore shows both add-tiles only while nothing is attached and **hides the other kind entirely** once one is chosen — swapping means removing what's there, which makes the exclusivity self-evident without a dialog explaining it. Limits mirror the server: `CreatePostMaxImages` (10 = `Album::MAX_PHOTOS`) and `CreatePostMaxVideoBytes` (25 MB = `Video::MAX_BYTES`), the latter checked via `FileLoader.sizeOf` *before* the file is read, since the point of the limit is not to hold an oversized clip in memory. Everything goes up as parts of one multipart `POST /posts` — the same transport as the avatar upload — as `images[]` (the brackets are what make Rack build an array) or `video`. Both upload endpoints build their parts through `common/data/network/MultipartParts.kt` (`FileUpload.asPart`, `String.asTextPart`), so how a file becomes a part is one edit rather than one per data source — it sits with the wire types rather than beside `FileUpload` in `common/data/files/`, since it is the OkHttp half of the pair and the HTTP rule in `ArchitectureTest` holds it there. Server-side the mirror of that is `UploadValidation.validate!`, the single sniff-then-check rule behind post images, post video, and the avatar.

    The form holds picked media as **content-URI strings, not bytes**: thumbnails render straight from the URI, and `FileLoader` reads them into `FileUpload`s once, at publish, so ten photos or a 25 MB clip aren't held for the whole composing session. That is why `CreatePostForm.toNewPost` takes the loaded media as a parameter rather than producing it. Re-picking images is additive and de-duplicated, since the system picker re-reports everything chosen in a session. **Video duration is the server's to derive**, not the client's: the upload carries the file alone and the duration comes back on the stored `Video`, which is what a published post's badge reads. The composer's *own* thumbnail is the one place that cannot wait for it — the clip has not been uploaded yet — so `VideoMetadataReader` (backed by `MediaMetadataRetriever`) reads it off the picked file for that badge alone, degrading to 0 rather than blocking a post. What it reads is never sent; `CreatePostMedia.Video` carries a duration and `NewPostMedia.Video` deliberately does not, which is the seam between the two. Coil needs its `VideoFrameDecoder` to preview a picked clip, which is the reason `MosaicApp` supplies the singleton `ImageLoader` — decoders are a loader-wide concern that can't be set at the call site.

    `PostApiMultipartTest` drives the **real Retrofit stack over MockWebServer** to pin this wire format. The other data-source tests swap in a fake service, which proves what the data source asks for but not what Retrofit serializes — and the part names and the omission of absent optional parts are exactly where client and backend have to agree.
  - `app/util/` — pure, unit-tested formatters, one file each (`RelativeTime.kt`, `CompactCount.kt`), with no project imports at all; `common/Formatting.kt` is the Android-aware half that turns their buckets into localized strings (and holds `formatVideoDuration`, which needs no resource). Noun-free reusable UI lives in `common/ui/`; UI that renders a domain object does not — `Avatar` takes a `User`, so it lives in `user/ui/`.

- **Dependency injection — Hilt.** `MosaicApplication` is the `@HiltAndroidApp` root (not `MosaicApp`, which is the root *composable*) and `MainActivity` an `@AndroidEntryPoint`; both stay empty of wiring. All production bindings live in `app/di/DataModule.kt`, `app/di/NetworkModule.kt` and `app/di/NavigationModule.kt`. Repositories are `@Singleton` so the `StateFlow` cache in `PostRepository` is shared across the feed and profile — a like toggled in one screen is immediately visible in the other (`ProfileRepository` explicitly composes the bound `PostRepository` so both screens see the same instance). ViewModels are `@HiltViewModel` with `@Inject` constructors, bound in screens via `hiltViewModel()` (from `androidx.hilt:hilt-lifecycle-viewmodel-compose` — the `hilt-navigation-compose` copy is deprecated). `ProfileViewModel` takes its runtime `userId` through **assisted injection** (`@HiltViewModel(assistedFactory = …)` + `hiltViewModel(key, creationCallback)`). Tests never touch Hilt: they construct ViewModels directly with fakes, which is why ViewModels keep plain constructor parameters. The repositories themselves carry no DI annotations (constructed in the module, not `@Inject`), keeping the data layer framework-free.

- **Theming** lives in `app/src/main/java/uno/lux/sample/app/theme/` and implements the **Mosaic** design system (a claude.ai/design handoff). `MosaicTheme` applies a fixed brand palette — indigo accent, warm-neutral surfaces, coral like-state, with full light/dark token sets in `Color.kt`. There is **no dynamic color** (the brand must stay consistent), and `surfaceTint` is transparent so cards keep their exact colour while still casting the soft shadow. `Type.kt` wires two **bundled variable fonts** (`res/font/`, OFL in `licenses/`): **Bricolage Grotesque** for the brand wordmark and post titles, **Manrope** for UI and body. Tokens with no Material role — the muted `textTertiary` and the coral `like` — are carried as `MosaicColors` via `LocalMosaicColors`. Wrap any new top-level Compose content (and `@Preview`s) in `MosaicTheme`. The light/dark choice is **user-controlled**: `MainActivity` collects the `ThemeMode` (Light/Dark/System) from `MainViewModel`, resolves it with `ThemeMode.isDark(isSystemInDarkTheme())`, and passes the result to `MosaicTheme(darkTheme = …)`; the settings screen changes it through `SettingsViewModel`. Edge-to-edge system-bar styling is re-applied in a `DisposableEffect` keyed on the resolved theme so the bar icons keep contrast.

## Surviving process death

**Rotation is the same problem, one notch weaker.** A configuration change recreates the Activity, so anything held in a plain `remember` is gone — the difference from a process death is only that ViewModels and repositories survive it. The rule that follows is: *any state a composable owns outright is `rememberSaveable`, not `remember`.* That covers a dialog's live selection and whether a sheet or dialog is open at all (`PostOverflowMenu`, `ReportPostDialog`), because a rotation mid-report must not throw the report away. `remember` is still right for state that is meaningless after a recreation — an `Animatable`, the `wasActive` latch that decides whether to replay a pop, a zoom gesture's transient offset.

A backgrounded app can be killed and later restarted straight onto the page it was killed on, and the two halves of that restart are restored by completely different machinery. **The back stack comes back; nothing else does.** `rememberBackStack` saves the `@Serializable` `BackStackEntry` keys — each a `Screen` plus its identity — into the instance state, and `rememberSaveableStateHolderNavEntryDecorator` brings back each entry's `rememberSaveable` state (a selected profile tab, a scroll position) under that same identity, which is why the id has to be a stored property rather than a regenerated default. Every repository, ViewModel and in-memory store, however, is built from scratch on the new process — so a screen must be able to rebuild everything it shows **from its `Screen` key alone**, and the key is therefore the place to put anything a restored page can't re-derive (`AlbumViewer` carries its image URLs, `FullscreenVideo` its url and title, for exactly this reason).

For a page that fetches, that means a **cold-start load**: check whether the stores already hold what the key names, and fetch when they don't. `EditProfileViewModel.load` does it for the signed-in user; `PostDetailViewModel.loadPost` does it through `PostRepository.load` (`GET /api/posts/:id`). A page reached the ordinary way never pays for this — it opens from a feed or profile whose fetch already filled the stores, and the check skips the request.

**An entity's absence from a store is ambiguous, so deletion says so explicitly.** "Not in `entities`" means either "nothing fetched it" or "it is gone", and a detail page can be looking at a post that *another* screen deletes — open a post, walk to the author's profile, delete it there. `PostRepository.delete` therefore records the ID in `deletedIds` before dropping the entity, and `PostDetailViewModel` overlays that on its own load state, so the page reads `NotFound` rather than spinning on a fetch nobody will make. `load` short-circuits on the same set, which also keeps "deleted" true offline. Nothing else needs it: the feed and profile resolve ordered IDs through `entities` and simply drop what vanishes.

Both endpoints that answer with a *single* post send the full projection, author embedded, so `PostRepository` takes the `UserRepository` and seeds it from `load` and `create` alike — the same thing `ProfileRepository` does for the authors riding along with a page of saved or liked posts. A sideloaded user belongs in the user store wherever it arrives from; leaving that to each caller is how a screen ends up with a post it can't draw a header for.

**An absent entity is three states, not one, on every screen that resolves one by id.** `PostDetailViewModel` and `ProfileViewModel` both make the distinction, and both had to: reading "the store has no such thing" as *not found* is correct only while the store is authoritative, which stops being true the moment the app can start on that page. `ProfileViewModel` gates `NotFound` behind `_hasLoaded` for exactly this reason — without it, a restored `Screen.Profile` showed "profile not found" for the whole of every cold-start fetch.

**An absent post is three states, not one.** This is what the fetch buys, and the trap it replaced: reading "the entity store has no such post" as *not found* is correct only when the store is authoritative, which it stops being the moment the app can start on a detail page. `PostDetailViewModel.PostLoad` therefore separates the fetch in flight (`Loading`), a 404 (`NotFound` — the server saying the post is gone, and nothing to retry), and a failed request (`Error`, with a retry button). `PostDataSource.fetch` returns `null` for the 404 rather than throwing, via `notFoundAsNull` — a missing resource is an answer, and only the other kind of failure is worth retrying. Deleting a post marks it `Missing` too, so the emptied store doesn't read as "not loaded yet" and flash a spinner behind the pop.

`BackStackRestorationTest` (instrumented) pins the first half with `StateRestorationTester.emulateSavedInstanceStateRestore()`, which saves the registry, throws the composition away and rebuilds it — the same round trip the platform performs. It walks one of every `Screen` through a restore, so a key that quietly stops being serializable fails there rather than in a user's hands, and it pins entry identity across the same round trip: two pushes of one screen keep separate state, while a screen that pins `sharedId` keeps one. It cannot emulate the empty stores, which is why the cold-start loading is covered by ViewModel unit tests instead.

**What the user typed is the one thing that has to be *saved*, not re-derived.** A fetch can be repeated; a half-written post cannot, so `CreatePostViewModel` and `EditProfileViewModel` persist their form through the `SavedStateHandle` Hilt injects — per back-stack entry, scoped by that entry's identity and riding in the same instance state as the `BackStackEntry` keys. `app/util/SavedDraft.kt` is the seam, `androidx.savedstate`'s serializer underneath it: `restoreDraft` decodes what the killed process left, `saveDraft` registers *where to read the draft from* rather than pushing every edit into the handle, so the platform pulls it at most once per save and typing costs nothing. That is why it takes a `() -> T` and not a `Flow<T>`, and why there is no collector to own. Serializing the form whole is also what keeps `CreatePostMedia` intact: flattening a draft into loose keys would lose which variant it is, and with it the photos-or-video exclusivity the closed hierarchy exists to guarantee.

Only the *form* is saved; an in-flight publish and the errors of a process that no longer exists are not, so a restored composer is idle and holds exactly what was typed. The editor's pristine snapshot is still re-read from the server, so restored edits keep reading as unsaved rather than silently becoming the new baseline.

This is the one part of the app whose tests are **instrumented rather than plain-JVM**, and deliberately so: a `SavedState` is a `Bundle`, so a JVM test could only ever have exercised a stand-in for the real encoding. `DraftRestorationTest` performs the round trip the framework does — ask the handle's provider to save, build a fresh handle from that state, rebuild the ViewModel from it — which is as close to a process death as a test gets. What no test can cover is whether the platform hands the entry's handle back at all; that was verified by killing the app with `adb shell am kill` on both screens.

Video playback position is still deliberately not restored.

## Compose performance — keeping recomposition tight

Holding recomposition to what actually changed is part of "idiomatic Compose" here, but it leans on the compiler rather than hand-tuning. The built-in Compose compiler (Kotlin 2.4.10) runs with **strong skipping on**, which shapes what's worth doing:

- **Don't reflexively wrap lambdas in `remember` or chase `@Stable`/`@Immutable` on every model.** Strong skipping auto-remembers lambdas (even ones capturing unstable values) and lets composables with *unstable* parameters still skip via instance equality. The domain models are technically unstable — `Post` carries a `java.time.Instant` and `List<…>` is an unstable type — yet feed and profile rows skip fine because each `LazyColumn` item is compared by instance.
- **Skipping is by instance, so a mutation must preserve identity for everything that didn't change.** `PostRepository` keeps its store as a `Map<PostId, Post>` and mutates with `_entities.update { it + (postId to updated) }`, which hands back the *same* `Post` instance for every entry except the toggled one — so a like/bookmark recomposes only that one `PostCard`. Mapping `copy()` over the whole collection (or otherwise producing fresh instances for unchanged entries) would recompose every visible row — avoid it.
- **Read snapshot-backed state in the smallest composable that uses it.** Scroll / pager / animation state read at a screen's top level invalidates that whole scope on every change. The album viewer keeps its page counter in a separate `PageIndicator` composable so swiping recomposes only the pill, not the pager or back button; prefer pushing such a read down into a child over hoisting it up.
- **Coalesce continuous signals with `derivedStateOf`.** When a boolean or bucketed value is derived from something that changes every frame (scroll offset, `overlappedFraction`), wrap it so readers recompose only when the *result* flips — see `ProfileTopBar`'s `scrolled` and the sticky-tab `tabInset`. The flip side: a signal that is *already* coalesced needs no wrapper, so `HomeScreen` reads `listState.canScrollBackward` directly (it only changes when crossing the very top).
- **Don't key a long-lived effect on state you only read inside it.** Keying a `LaunchedEffect` on a frequently-replaced value restarts it on every change. The feed's inline-autoplay collector reads the current posts through `rememberUpdatedState` and keys only on the stable `listState`/playback, so a like toggle no longer tears down and restarts its `snapshotFlow`. The auto-play *setting* is a key rather than a `rememberUpdatedState` read, and deliberately so: it flips only when the user changes it, and the restart re-reads the current layout, so switching auto-play on plays the video already on screen instead of waiting for the next scroll.
- **Animate in the draw/layer phase when you can.** The like/bookmark "pop" reads its `Animatable` inside `graphicsLayer { scaleX = … }`, so each frame re-runs the layer, not composition. Composition-scope animation (`animateColorAsState`, `animateFloatAsState`) is still right for short, intentional transitions where recomposing a small subtree per frame costs nothing — that's idiomatic, not something to optimize away.

## Code style

**Separate logical sections within a function with a blank line.** When a function body groups setup/declarations together and then does something with them, put a blank line between the groups. This applies equally to plain Kotlin functions and composables.

```kotlin
// Declarations first, then a blank line before the work that uses them.
override fun profile(userId: String): Flow<Profile> =
    postRepository.posts.map { posts ->
        val userPosts = posts.filter { it.authorId == userId }
        val pinned = pinnedByUser[userId].orEmpty()

        Profile(...)
    }

// In composables: state declarations first, then a blank line before each UI element.
@Composable
private fun OverflowMenu(...) {
    val context = LocalContext.current
    var showSheet by remember { mutableStateOf(false) }

    IconButton(...) { ... }

    if (showSheet) {
        PostOverflowSheet(...)
    }

    if (showReportDialog) {
        ReportPostDialog(...)
    }
}
```

**Break function parameters onto separate lines when there are three or more.** Two parameters fit comfortably inline; three or more get one per line with a trailing comma on the last.

```kotlin
// 2 params — inline is fine
fun FeedTopBar(elevated: Boolean, onOpenSettings: () -> Unit)

// 3+ params — one per line
fun HomeScreen(
    uiState: HomeUiState,
    isRefreshing: Boolean,
    actions: HomeActions,
    onOpenSettings: () -> Unit,
)
```

**An expression body that ends in a trailing lambda keeps the brace on the declaration line.** Never break after the `=` and push the whole call onto the next line — break *inside* the lambda instead. The declaration line then reads as a signature plus what it delegates to, and the body sits where a block body's would.

```kotlin
// Yes — the brace closes the declaration line, the work is indented under it.
override fun onToggleLike(postId: PostId) = launchCatching {
    postRepository.toggleLike(postId)
}

// No — a continuation line that has to be read backwards to find what it belongs to.
override fun onToggleLike(postId: PostId) =
    launchCatching { postRepository.toggleLike(postId) }
```

What the lambda *is* decides whether it stays inline when it fits. A **block of work** — anything launched, a coroutine body, a test body — always takes its own lines, so the whole family of actions in a ViewModel reads as one shape rather than splitting on which ones happened to fit in the line budget. A **small value expression** stays inline until it no longer fits:

```kotlin
// Value expressions — inline, and only the one that overflows expands.
override fun onNicknameChange(value: String) = updateForm { it.copy(nickname = value) }

override fun onAgeChange(value: String) = updateForm { form ->
    form.copy(age = value.filter { it.isDigit() }.take(3))
}
```

**Use named arguments at call sites when the value doesn't self-document its role.** A single-argument call is almost always clear; a multi-argument call where some values are bare literals, same-typed, or opaque without context should use names. Two specific cases that always warrant names:

- *Lambda type parameters* — when a function type has a non-obvious parameter, name it at the type declaration so every call site is self-explanatory without back-tracking to the definition. E.g. `(Album, initialIndex: Int) -> Unit`, not `(Album, Int) -> Unit`.
- *Coordinate and geometry constructors* — `Offset`, `Size`, and similar value types take `x`/`y` or `width`/`height` that are easy to transpose; always name them: `Offset(x = 0f, y = thickness / 2f)`.

Exception: enum constructor entries (`HOME(R.string.nav_home, R.drawable.ic_home)`) — Kotlin does not allow named arguments for enum constructors, so positional is the only option.

**A file-level overview comment is a block comment (`/* ... */`), not a KDoc (`/** ... */`).** Kotlin has no formal file-level KDoc target, and a KDoc immediately followed by another KDoc — the first declaration's own — is never allowed by ktlint's `no-consecutive-comments`, even with a blank line between them. A block comment never collides with it, and it costs nothing: a floating KDoc above another KDoc was never rendered as attached to the declaration below it anyway.

## Localization

All user-facing text lives in `app/src/main/res/values/strings.xml` and is read with `stringResource(...)` — never hardcode display strings in Kotlin. Exception: strings that contain no actual words — only numbers, punctuation, or symbols (e.g. `"${page} / $total"`) — are fine as plain Kotlin interpolation; there is nothing for a translator to change. Navigation labels are `@StringRes` IDs on the `AppDestinations` enum.

Computed text (relative time, compact counts) keeps its *logic* pure and testable in `app/util`: `relativeTime()` and `compactCount()` return structured buckets (`RelativeTime`, `CompactCount`) with no display strings, and `common/Formatting.kt`'s `asText()` resolves a bucket to a localized resource. That's how format tokens like "5m" or "1.2K" stay localizable without making the formatters depend on Android. Post *content* in `SampleData` is stand-in data, not UI chrome, so it remains literal.

**Languages shipped: English (`values/`, the default) and Czech (`values-cs/`).** Add a language by adding a `values-<code>` folder and an `AppLanguage` entry. **The app is deliberately not listed under the system's per-app language settings**: the manifest declares no `android:localeConfig` and the build script does not set `generateLocaleConfig`, which is the documented way to signal that the language is not the system's to change. The in-app picker is the only way in, and that is what keeps `AppLocaleRepository` the single writer — its `StateFlow` mirrors the delegate and is only ever updated by its own `setLanguage`, so an external writer would silently leave it stale across the activity recreation a locale change triggers (the `@Singleton` repository outlives it). Do not re-enable `generateLocaleConfig` without also making the repository re-read `AppCompatDelegate.getApplicationLocales()` on every activity create. Anything counted needs `<plurals>` + `pluralStringResource(...)`, not a `%d` format string: Czech buckets on `one`/`few`/`many`/`other`, so "2 komentáře" and "5 komentářů" differ. Strings that read the same in every locale — the `Mosaic` wordmark, the language endonyms `English`/`Čeština` — are marked `translatable="false"` rather than duplicated per locale.

**Switching language uses the per-app language APIs, so the app persists nothing itself.** `AppLocaleRepository` is the seam (`InMemoryAppLocaleRepository` for tests); `AppCompatLocaleRepository` calls `AppCompatDelegate.setApplicationLocales(…)`, which forwards to the framework's `LocaleManager` on Android 13+ and, below that (`minSdk` is 26), stores the choice itself — that backport is why `androidx.appcompat` is a dependency, why `MainActivity` extends `AppCompatActivity` (its delegate applies the locale on cold start; *no* AppCompat UI is used), why `Theme.Mosaic` descends from `Theme.AppCompat`, and why the manifest declares `AppLocalesMetadataHolderService` with `autoStoreLocales=true`. Applying a language recreates the activity, which re-reads resources; the Nav3 back stack survives because it is saveable.

**There is no "System" language option, and that is deliberate**: with only two languages shipped, a device set to a third would leave such a choice silently meaning "English". Instead the device seeds the choice *once*. On first launch — the per-app locale list still empty — `MainActivity` calls `MainViewModel.resolveInitialLanguage()`, which pins the first of the device's preferred languages that we ship (`AppLanguage.fromLanguageTags`, matching in the device's own order of preference and ignoring region and Unicode-extension subtags: a real list reads `en-US-u-fw-mon-mu-celsius,cs-CZ-u-…`), falling back to `AppLanguage.Default` (English) when we ship none of them. It is a no-op once anything is stored — which is the point, since the stored language is what keeps the app steady when the device's language later changes. The `AppLocaleRepository` is injected into `MainViewModel` like every other dependency, but the *call* stays in `MainActivity.onCreate` — after `super.onCreate`, since the locale APIs need the AppCompat delegate to have attached — rather than in the ViewModel's `init`.
